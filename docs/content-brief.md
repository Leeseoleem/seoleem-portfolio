# 콘텐츠 브리프

> 화면마다 어떤 정보가 들어가는지, 어디에 쓰이는지, 얼마나 써야 하는지. 빈칸을 채우면 그대로 코드에 옮긴다.
> 채울 때 지킬 것은 맨 아래 "작성 규칙"에 있다. 수치는 실제로 측정한 값만 쓴다.

---

## 0. 한눈에 보기

| 화면 | 역할 | 사람이 보는 시간 | 들어갈 것 |

## 1. 부팅 화면

**어디**: `lib/desk/screen-canvas.ts`의 `introLines`. 타자기처럼 한 글자씩 찍힌다. 7초 안에 다 나와야 하므로 줄 수는 5줄이 한계다.

**쓰는 법**: 명령줄 출력처럼 `>`로 시작하는 짧은 문장. 각 줄 20자 안. 첫 줄과 마지막 줄은 "불러오는 중 / 준비하는 중"류 진행 문구로 두고, 가운데 2~3줄이 진짜 내용이다. 여기서 보는 사람이 얻어가야 할 것은 하나다: "디자인과 개발을 잇는 프론트 개발자."

**지금 들어 있는 것** (임시):
```
> seoleem 포트폴리오를 불러오는 중...
> 디자인과 개발을 잇는 프론트엔드 개발자
> Figma에서 시작해서 React로 끝낸다
> 출시한 앱 2개, 진행 중인 프로젝트 3개
> 책상을 준비하는 중...
```
넷째 줄의 숫자는 확인 필요. 실제와 다르면 고치거나 뺀다.

**채울 것**:
```
1줄:
2줄:
3줄:
4줄:
5줄:
```

## 5. 모니터 · 프로젝트 창 (프로젝트마다 하나)

**어디**: `components/desk/surfaces/MonitorScreen.tsx`의 `WindowBody` (`kind: 'project'`). 지금은 골격(회색 막대)이고, 데이터 구조를 만들어 `xp-apps.ts`에 넣을 예정이다. 창 크기 620×460이라 스크롤이 생기지만, 첫 화면에 보이는 건 위 400px이다. 그 안에 스크린샷 하나와 문제·역할이 들어와야 한다.

**구조**: 문제 → 내 역할 → 구현 → 결과. 이 순서를 바꾸지 않는다.

**프로젝트마다 채울 것**:
```
이름:
기간:                      (예: 2025.03 ~ 2025.09, 7개월)
인원과 내 역할:            (예: 4인, 팀장 · 프론트 · 디자인 시스템)
한 줄 소개:                (30자 안. 폴더 창에도 쓴다)
스택:                      (쉼표로. 5개 안)
링크:                      배포 URL / GitHub / 발표 자료 (있는 것만)

[문제] 무엇을 풀려고 했나. 2~3문장.

[역할] 내가 맡은 것. 팀 프로젝트면 남이 한 것과 구분되게. 2~3문장.

[구현] 어떻게 만들었나. 기술 결정과 그 이유. 3~5문장 또는 불릿 3~5개.
       불릿은 "행동 + 결과" 구조.
       나쁨: React를 사용하여 프론트엔드 개발 담당
       좋음: 체크리스트 저장을 낙관적 업데이트로 바꿔 저장 시 화면 멈춤 제거

[결과] 무엇이 달라졌나. 측정한 수치가 있으면 수치, 없으면 정성적 결과. 1~3문장.
       나쁨: 렌더링 성능 30% 개선 (측정 안 함)
       좋음: 리스트 가상화로 수백 개 항목에서도 스크롤이 끊기지 않게 개선

[배운 것] 다시 하면 다르게 할 것. 1~2문장. (선택)

스크린샷: 대표 1장 + 추가 2~3장. 파일 경로 또는 "준비 중".
          창 안 비율은 4:3에 가깝게. 폰 화면 캡처는 세로라 나란히 2장이 맞는다.
```

각 프로젝트를 위 양식으로 하나씩. 처음 채울 때는 대표 프로젝트 하나만 완성하고 나머지는 이름·한 줄·스택만 있어도 된다.

## 6. 모니터 · 소개 창

**어디**: `WindowBody` (`kind: 'article'`, id `about`). 창 520×400. 첫 화면에 3~4문단.

## 작성 규칙 (전체 공통)

1. 포지셔닝은 하나다. 디자인과 개발을 잇는 프론트 개발자. 핸드오프를 받기만 하는 게 아니라 기획·디자인 시스템 단계부터 참여한다. 이걸 흐리는 문장은 뺀다.
2. 레벨은 신입~주니어. 시니어처럼 들리는 문장("아키텍처를 설계", "팀을 리드")은 사실이 아니면 쓰지 않는다. 사실이면 구체적 사실로 쓴다("7개월 캡스톤 팀장, 일정 관리와 디자인 시스템 정리 담당").
3. 수치는 측정한 것만. 없으면 정성적 결과로 끝낸다.
4. 상투 형용사 금지. 성실한, 책임감 있는, 열정적인, 꼼꼼한. 대신 그걸 보여주는 사실.
5. 프로젝트는 문제 → 역할 → 구현 → 결과 순서.
6. 이력서 불릿은 명사형 종결, 소개는 존댓말 문서체, 부팅 화면과 HUD는 명령줄 톤.
7. 화면마다 글자 수 한도가 있다. 넘치면 스크롤이 생기는 게 아니라 잘린다고 생각하고 쓴다.

## 우선순위

전부 채우기 전에 사이트가 "완성처럼" 보이려면 이 순서다.

1. 9-2 독 링크 (5분, 없으면 배포 못 함)
2. 4 + 5 대표 프로젝트 하나 완성 (모니터의 존재 이유)
3. 6 소개 창
4. 1 부팅 문구 확정 (숫자 확인)
5. 10 공책 3장
6. 나머지
