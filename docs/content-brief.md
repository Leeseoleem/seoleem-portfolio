## 5. 모니터 · 프로젝트 창

**어디**: `components/desk/surfaces/MonitorScreen.tsx`의 `WindowBody` (`kind: 'project'`). 620×460.

**구조 (확정)**: 프로젝트 하나는 하나의 창으로 열고, 창 안에서 `이전 / 다음`으로 장을 넘긴다.

웹에서는 PDF 포트폴리오의 모든 장을 그대로 옮기지 않는다. 프로젝트마다 아래 세 종류만 남긴다.

```text
프로젝트 소개
    ↓
서비스 구조
    ↓
Engineering Case
```

프로젝트 3개 모두 대표 Engineering Case 2건씩, 4장으로 구성한다.

```text
핏플       4장
가라챠토   4장
우리두     4장
```

공통 원칙:
- 프로젝트 소개 장에 서비스 설명, 기간, 팀, 역할, 기술 스택, 외부 링크와 대표 화면 2장 정도를 함께 보여준다.
- `주요 화면`을 별도 장으로 만들지 않는다.
- 서비스 구조 장은 **설명문 없이 구조도만** 보여준다.
- 서비스 구조도는 레트로 데스크톱 콘셉트에 맞춰 고정폭 폰트와 ASCII 박스·선으로 표현한다.
- Engineering Case는 웹 화면에 맞게 `문제 → 결정 → 판단 근거 → 결과`까지만 보여준다.
- `이후 기준`과 `그 밖의 기술 판단`은 웹 프로젝트 창에서는 생략한다. 상세 근거는 PDF 포트폴리오와 면접에서 이어갈 수 있게 남겨 둔다.
- 프로젝트마다 핵심 판단 2건 이상을 억지로 추가하지 않는다.

하단 탐색은 현재 장 번호와 앞뒤 장의 이름을 함께 보여준다.

```text
‹ 서비스 구조          3 / 4          Web ↔ Native RPC ›
```

기본 조작은 버튼 클릭이며 키보드 `← / →` 이동도 지원한다. 1장만 보고 프로젝트를 이해할 수 있고, 더 궁금한 사람만 다음 장으로 들어가게 한다.

### 3 / 4 Engineering Case 01

**헤더 분기를 라우트 설정으로 옮겨 변경 지점 단일화**

**문제**  
라우트가 30개를 넘으며 페이지마다 헤더 분기가 쌓였고, 정책 변경 때 여러 파일을 함께 수정해야 했습니다.

**결정**  
헤더 구성을 라우트 설정 맵으로 옮기고 구간 정책은 섹션 패턴으로 처리했습니다. 헤더 5종은 TypeScript discriminated union으로 구분했습니다.

**판단 근거**  
헤더는 개별 화면 상태보다 라우트에 따라 정해지는 UI 정책에 가까워 Context보다 설정 구조가 적합하다고 판단했습니다.

**결과**  
페이지별 분기가 사라지고 변경 지점이 설정 맵으로 모였습니다. 잘못된 헤더 조합도 컴파일 단계에서 차단됩니다.

### 4 / 4 Engineering Case 02

**웹·네이티브 호출을 하나의 RPC 규약으로 통합**

**문제**  
저장소, 외부 링크, 앱 종료처럼 네이티브 기능이 늘며 기능별 메시지와 콜백이 함께 늘어날 수 있었습니다.

**결정**  
요청은 `{ id, method, payload }`, 응답은 `__bridgeResolve(id, ok, value)`로 통일하고 요청별 Promise를 pending Map으로 관리했습니다.

**판단 근거**  
기능별 메시지를 추가하는 대신 웹에서 모든 네이티브 기능을 같은 Promise 인터페이스로 다루고 싶었습니다.

**결과**  
FCM 토큰과 앱 버전 조회까지 같은 규약으로 확장했고, 구버전 앱에는 메서드 존재 여부를 확인하는 호환 규칙을 적용했습니다.

### 3 / 4 Engineering Case 01

**전곡 검색 확장 중 88.5% 누락 확인, 검색 구조 재설계**

**문제**  
검색 범위를 11,519곡으로 넓힌 뒤 확인해 보니 기존 검색 대상은 1,319행뿐이었고, 카탈로그의 88.5%가 빠지고 있었습니다.

**결정**  
검색을 PostgreSQL RPC로 옮기고 부분 일치, 별칭, trigram, 자모 편집거리 등을 함께 적용했습니다. 인기 차트와 전체 카탈로그 결과도 분리했습니다.

**판단 근거**  
`ai`는 전체 카탈로그에서 412건이 매칭돼도 하나의 결과 제한에서는 노출되지 않을 수 있었습니다. 정확도뿐 아니라 어떤 결과를 보여줄지도 함께 해결해야 했습니다.

**결과**  
전곡 검색이 가능해졌고, 곡 그룹화도 DB로 옮겨 행이 아닌 곡 기준으로 결과를 반환하도록 했습니다.

### 4 / 4 Engineering Case 02

**SSR 미지원 환경에 맞춰 미니앱 구조 재설계**

**문제**  
Next.js 웹은 Server Component에서 데이터를 조회했지만 Apps-in-Toss에서는 SSR을 사용할 수 없었습니다.

**결정**  
별도 Vite 앱에서 클라이언트 Supabase 조회와 RLS를 사용하고 라우팅은 React Router로 다시 구성했습니다.

**판단 근거**  
브라우저가 DB를 직접 조회하는 환경에서는 화면 코드가 아니라 실제 DB 정책에서 접근 권한을 제한해야 했습니다.

**결과**  
같은 데이터를 사용하면서 웹은 서버 조회, 미니앱은 클라이언트 조회와 RLS를 사용하는 구조로 분리했습니다.

추가 설명문 없이 아래 구조도만 보여준다.

```text
              사용자
```

### 3 / 4 Engineering Case 01

**동시 401 토큰 재발급 단일화**

**문제**  
여러 API가 동시에 401을 받으면 각 요청이 같은 rotating Refresh Token으로 재발급을 시도해 세션이 끊길 수 있었습니다.

**결정**  
진행 중인 재발급 Promise를 하나만 유지하고 뒤따르는 요청은 같은 결과를 기다리도록 했습니다.

**판단 근거**  
필요한 것은 요청 순서를 맞추는 것이 아니라 여러 요청이 하나의 재발급 결과를 공유하는 것이었습니다.

**결과**  
동시에 여러 요청이 만료돼도 재발급은 한 번만 수행됩니다. 네트워크 오류와 실제 세션 만료도 구분해 처리했습니다.

### 4 / 4 Engineering Case 02

**DnD 라이브러리 검증 후 직접 구현으로 전환**

**문제**  
항목 정렬과 리스트 밖 휴지통 삭제를 함께 지원해야 했지만 `reanimated-dnd`가 외부 drop zone까지 지원하는지는 문서만으로 알기 어려웠습니다.

**결정**  
소스를 확인해 `useSortable`의 `DropContext` 참조가 0건임을 확인하고 라이브러리를 제거했습니다. 이후 Gesture Handler와 Reanimated로 직접 구현했습니다.

**판단 근거**  
라이브러리에 화면 구조를 맞추면 필요한 인터랙션을 포기하거나 우회 로직이 늘어날 가능성이 있었습니다.

**결과**  
기존 화면 구조를 유지하면서 정렬과 외부 삭제 영역을 함께 구현했고, 지원되지 않는 동작을 위한 우회 코드도 남기지 않았습니다.

## 10. 공책

**어디**: `components/desk/surfaces/NotebookPages.tsx`의 `PAGES`. 720×940 세로.

**성격 (확정)**: 공책은 개발 구조를 설명하는 곳이 아니라 **UI와 비주얼 디자인 작업을 보여주는 공간**이다.

공간별 역할을 겹치지 않게 나눈다.
```text
모니터   개발 결과 · 구조 · 기술 판단
공책     UI 설계 · 비주얼 방향 · 디자인 시스템 · 화면 구성
핸드폰   연락처 · 외부 채널 · 프로젝트 진입
서류     PDF 이력서 페이지 열람
```

공책에서는 긴 기술 설명을 하지 않는다. 실제 화면, Figma 산출물, 컬러·타이포·컴포넌트, 화면 변화 등을 중심으로 보여주고 글은 장 제목과 프레임 이름표뿐이다.

**형식 (확정)**: 짜임은 iOS 화면 규칙을 따른다. 모든 글은 왼쪽 한 줄에 맞춰 서고, 큰 제목 하나가 장을 이끈다. 장 맨 위가 34px 제목이고, 그 아래 한 단계 어두운 판에 프레임을 이름표와 함께 줄 단위로 얹는다. 프로젝트 이름과 쪽번호는 장 바닥에 한 줄로 둔다. 판은 장 높이를 채우지 않고 담긴 화면만큼만 차지한다. 안내 문장, 설명글, 밑줄, 점선 같은 장식은 두지 않는다.

글자는 다섯 단계뿐이다. 34 제목, 17 본문과 목차, 15 보조, 13 바닥글과 쪽번호, 12 이름표. 층은 크기와 굵기와 색으로만 나눈다. 프레임을 누르면 전체 화면으로 크게 본다(같은 장 안에서 좌우 이동, Esc로 닫기). 프로젝트마다 **컴포넌트 → 화면 시안** 순서다.

표지는 잉크 펜 필기체(La Belle Aurore) 제목과 한 줄 설명, 그 아래 프로젝트 목차를 한 덩어리로 묶어 장 가운데에 놓는다. 목차는 한 판 위에 줄을 얹은 형태다(아이콘 44, 이름, 쪽번호, 꺾쇠, 줄 높이 60, 구분선은 글자 자리부터). 프로젝트마다 간지 한 장으로 열고, 간지는 프로젝트 로고(56)와 이름을 한 줄에 놓고 그 아래 그 프로젝트 안의 목차만 둔다. 프로젝트 순서는 이력서와 같은 핏플, 가라챠토, 우리두다.

공책 오른쪽 가장자리에는 프로젝트마다 인덱스 탭이 붙어 있고, 탭이나 목차를 누르면 그 프로젝트의 간지로 넘어간다. 이때 위치를 한 번에 옮기지 않고 시간에 따라 이어서 옮겨, 사이의 장이 한 장씩 주르륵 넘어간다(약 1.4초 안). 한 번에 옮기면 목적지 장이 먼저 드러난 채로 그 위에서 종이만 펄럭인다. 넘어간 장의 탭은 장과 함께 왼쪽으로 간다. 장을 다 넘기면 뒤표지가 나오고 `처음으로` 단추 하나만 있다.

3D 공책의 표지 라벨에도 같은 필기체로 `Design Notes`를 쓴다(`lib/desk/notebook-label.ts`, 캔버스 텍스처). 닫힌 공책과 펼친 첫 장이 같은 제목을 든다.

자료는 Figma 프레임 단위 2x PNG 내보내기가 기본이다(가라챠토). 우리두는 탭 하나를 통째로 내보낸 보드, 핏플 2.x는 코드에서 정리한 보드라 폰 화면 하나가 작게 보이는데, 이 경우는 전체 화면 보기가 그 역할을 맡는다. 내용은 `lib/desk/content/notebook.ts`, 이미지는 `public/notebook/{프로젝트}/*.webp`.

**장 구성**:
```text
1장 (표지)
   제목: Design Notes (필기체)
   설명: 프로젝트별로 직접 디자인한 화면과 컴포넌트에 대한 기록
   목차: 프로젝트 아이콘과 이름, 시작 장 번호

2장 (핏플 간지)   3~6장 (핏플 2.x)
   Figma 시안 없이 코드에서 만든 버전이라, 완성된 앱 코드에서 뽑아 정리한 보드다(decision-backlog B07).
   디자인 토큰 1장(color, typography, spacing) 뒤에 화면 3장(auth / home / plan+route). 앱 흐름 순서다.

7장 (가라챠토 간지)   8~12장 (가라챠토)
   컴포넌트 2장(곡 상세+챗봇 / 설정과 시트) 뒤에 화면 시안 3장. 한 장에 폰 화면 셋이다.
   TOP100 번역, TOP100 원문, 목록 스크롤 / 검색 추천어, 검색 결과, 설정 시트 / 챗봇 시트, 챗봇, 곡 상세

13장 (우리두 간지)   14~23장 (우리두)
   Figma 탭 하나를 통째로 내보낸 보드 단위다. 컴포넌트 4장(common+auth / home+challenge / uri+calendar / my) 뒤에
   화면 시안 6장(onboarding / home / challenge / uri / calendar / my). 탭 순서를 그대로 따른다.
```

프로젝트 구성은 실제 보유한 디자인 자료를 보고 바꿔도 된다. **공책의 목적은 프로젝트 수를 맞추는 것이 아니라, 실제로 보여줄 만한 디자인 작업을 선별하는 것**이다.

모니터의 서비스 구조도나 Engineering Case를 공책에서 다시 설명하지 않는다. 같은 프로젝트를 다루더라도 모니터는 개발 판단, 공책은 시각 설계라는 서로 다른 역할을 갖는다.

## 11. 서류 (PDF 이력서 뷰어)

**어디**: `components/desk/surfaces/DocumentSheets.tsx`. 600×840.

**역할**: 책상 위에 놓인 실제 이력서처럼, 보유 중인 `resume.pdf`를 페이지 단위로 한 장씩 보여준다.

웹용 프로필이나 스킬 요약을 새로 작성하지 않는다. PDF 원본 자체가 이 공간의 콘텐츠다.

**표현 방식**:
```text
┌──────────────────────────┐
│                          │
│     resume.pdf  1 / N    │
│                          │
│       [ PDF PAGE ]       │
│                          │
│                          │
├──────────────────────────┤
│  ‹ 이전           다음 › │
└──────────────────────────┘
```

- 한 번에 PDF 한 페이지만 보여준다.
- PDF가 여러 페이지라면 `이전 / 다음`으로 넘긴다.
- 마지막 페이지를 넘겨도 다시 처음으로 순환시키지 않는다.
- 원본 PDF의 타이포, 배치, 연락처, 프로젝트 내용을 그대로 보여준다.
- 별도의 웹용 요약 문구나 프로젝트 설명을 덧붙이지 않는다.
- 모니터의 이력서 아이콘은 **다운로드**, 책상 위 서류는 **열람**으로 역할을 구분한다.
- 실제 파일은 두 공간 모두 `/public/resume.pdf` 하나를 사용한다.

## 작성 규칙 (전체 공통)

1. **포지셔닝은 하나다. 반복되는 문제를 구조로 해결하는 프론트엔드 개발자.** 근거는 세 가지다. 같은 판단이 반복되면 책임을 다시 나눈다, 문서나 이름이 아니라 직접 확인한 사실로 판단한다, 정한 방향은 출시와 운영까지 이어간다.
2. **"디자인과 개발을 잇는", "디자이너의 눈으로 개발하는" 류의 브릿지 표현은 쓰지 않는다.** Figma와 디자인 토큰은 작업 도구와 방식으로만 언급한다.
3. 레벨은 신입~주니어. 시니어처럼 들리는 추상적인 표현보다 실제로 한 행동과 결과를 쓴다.
4. **수치는 이력서·포트폴리오 최종본에서 이미 검증된 것만 사용한다.** 새 수치를 만들지 않고 단위도 그대로 지킨다. 예를 들어 가라챠토의 `1,319`는 곡이 아니라 행이고, `11,519`는 곡이다.
5. 상투적인 자기평가 표현은 쓰지 않는다. `성실한`, `책임감 있는`, `열정적인`, `꼼꼼한` 대신 실제 행동으로 보여준다.
6. **프로젝트 하나는 하나의 창으로 열고 장 단위로 넘긴다.** 모든 프로젝트는 `소개 → 서비스 구조 → Engineering Case 01 → Engineering Case 02` 4장으로 구성한다.
7. **Engineering Case는 `문제 → 결정 → 판단 근거 → 결과`까지만 보여준다.** PDF 포트폴리오에 있는 추가 판단과 `이후 기준`을 웹에 전부 반복하지 않는다.
8. **프로젝트 장은 스크롤 없이 한 화면 안에서 읽히게 구성한다.** PDF 서류처럼 페이지 넘김이 명시된 공간은 페이지 이동을 사용하고, 별도로 스크롤을 의도한 화면이 아니라면 내용이 넘치지 않게 줄인다.
9. **공간마다 역할을 겹치지 않는다.** 모니터는 개발 결과·구조·기술 판단, 공책은 디자인, 핸드폰은 연락과 바로가기, 서류는 PDF 이력서 열람을 맡는다.
10. **서비스 구조 장은 설명문 없이 ASCII 구조도만 보여준다.** 고정폭 폰트와 `│ ─ ┌ ┐ └ ┘ ↓ ↕` 같은 문자를 사용해 레트로 데스크톱 콘셉트에 맞춘다.
11. 소개와 Engineering Case는 존댓말 문서체를 사용한다. 부팅 화면과 HUD는 명령줄 톤, 휴지통은 짧은 판단 문장으로 쓴다.
12. 같은 정보가 여러 오브젝트에 필요하다면 역할을 달리한다. 예를 들어 이력서는 모니터에서 **다운로드**, 책상 위 서류에서는 **페이지 단위 열람**으로 제공한다.

## 확인 필요 항목

구현 전에 아래 자산과 선택지만 확인한다.

1. **프로젝트 대표 화면 이미지**  
   핏플, 가라챠토, 우리두의 소개 장에 넣을 실제 화면을 최종 선정한다. 기본 2장씩을 기준으로 한다.

2. **핸드폰 앱 타일 구성과 아이콘**  
   `핏플 · 가라챠토 · 우리두` 3개를 한 줄에 둔다. 아이콘은 세 프로젝트 모두 실제 앱 아이콘을 받아 `public/icons/`에 넣었다.

3. **PDF 이력서 연결**  
   보유 중인 PDF를 `/public/resume.pdf`에 연결한다. 모니터에서는 다운로드, 책상 위 서류에서는 페이지 단위 열람으로 사용한다.

4. **공책 디자인 자료**  
   실제 Figma 화면, 리뉴얼 전후, 디자인 토큰, 컴포넌트 등 보유 자료를 확인한 뒤 가장 좋은 디자인 작업 3개를 선별한다. 프로젝트 수를 맞추기 위해 약한 자료를 넣지 않는다.

5. **OG 공유 이미지**  
   3D 책상 기본 시점 1200×630 캡처를 준비한다. 모니터가 켜진 상태를 기본안으로 한다.

## 구현 우선순위

1. **프로젝트 탐색과 핏플 창**  
   프로젝트 폴더 → 핏플 소개 → 서비스 구조 → Case 2건까지 먼저 완성한다.

2. **가라챠토 · 우리두**  
   확정된 프로젝트 구조에 맞춰 나머지 프로젝트 창을 채운다.

3. **소개 · 부팅 · HUD**  
   개발자 소개와 첫 진입 경험을 현재 확정 문구에 맞춘다.

4. **휴지통**  
   프로젝트 본문에서 덜어낸 선택 과정을 짧은 항목으로 연결한다.

5. **핸드폰**  
   외부 링크와 프로젝트 바로가기를 연결한다. 프로젝트 타일 수는 실제 화면을 보고 최종 확정한다.

6. **공책**  
   선별한 실제 디자인 자료로 페이지를 구성한다.

7. **이력서 다운로드 · PDF 서류 뷰어**  
   하나의 `resume.pdf`를 다운로드와 페이지 열람 두 방식으로 연결한다.

8. **메타 · OG 이미지**  
   탭 제목, 공유 설명, 공유 이미지를 적용한다.

9. **종료 · 오류 화면**  
   마지막으로 주변 상태 화면의 문구와 동작을 맞춘다.
